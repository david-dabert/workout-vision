DEFECTS

1. A set is remembered as kept once collected, not once its file is saved, so a tab eviction before sharing loses those sets.
- Where: /home/user/workout-vision/src/collect-batch-main.js:146-148 records a set in `memory.collected` and moves `memory.next` as soon as it is collected. The file itself (`row.blob`) lives only in page memory until Share or Download.
- Scenario: this is the very case the reload fix was built for. David collects 12 of 20 sets on his iPhone. iOS evicts the Safari tab (he switched to Photos to check a count) before he tapped Share. After the reload the 12 files no longer exist anywhere.
  - He picks the 20 videos again. Each of the 12 now ends as "Same video as set N: not kept." (`twinOf` finds them in `memory.collected`, line 142-143). The page will not rebuild files it never handed over.
  - His only way out is "Start again from set 1". Its confirm (line 184) tells him to "Keep the files of sets 1 to 12 first", which he cannot do because they are gone.
  - The same refusal hits a deliberate re-collection of an old video on a later day, since the memory never expires.
- Smallest failing test: an e2e test on collect-batch.html. Stub `collectSet` to return a fixed blob and sha256, for example through a `window.__collectSet` hook, or move the record rule into a pure function. Pick a.mov, collect, reload without sharing, pick a.mov again, collect. Expect the row to reach 'done', not the note "not kept".
- Fix direction: push to `memory.collected` and advance `memory.next` only once the file is handed over (Share resolved, or Download tapped). Until then, keep only the numbers already given, so no new file takes a number an earlier file has.

2. Two tabs overwrite each other's memory and hand out the same set numbers.
- Where: /home/user/workout-vision/src/collect-batch-main.js:29-30. `memory` is read once at load and written whole on each collected set.
- Scenario: collect-batch.html is open in two Safari tabs. Tab A collects sets 1 to 5 and stores next=6. Tab B, loaded earlier with next=1, picks and numbers from 1, so it produces a second set01 to set05. B's writes then erase A's fingerprints.
- Smallest failing test: two pages in one Playwright context, both opened, then a collect in A (needs the same stub as defect 1). B's next pick should start at "Set 6". Re-reading localStorage inside `appendRows` and before `remember()` would fix it.
